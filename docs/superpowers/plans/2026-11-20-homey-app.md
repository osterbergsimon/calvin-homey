# Calvin app for Homey Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Homey Pro app, installed with the Homey CLI, that shows each Calvin screen as a Homey
device that can be turned on or off, shows the screen's Screen power mode (Schedule, Always on or
External), and is watched for going offline.

**Architecture:** A Homey Compose app in TypeScript. Everything that talks to Calvin or decides
state lives in `lib/` with no Homey imports and is unit-tested against a fake Calvin on
`127.0.0.1`; thin Homey classes (`app.mts`, `drivers/screen/driver.mts`, `device.mts`, `api.mts`)
wire it to the SDK and are tested against a stub `homey` module. One app-level connection, one
poller per connection, every 30 s.

**Tech Stack:** Homey Apps SDK v3, Homey CLI (`homey` npm package), TypeScript, Node.js 22, Vitest,
ESLint with typescript-eslint, GitHub Actions.

**Spec:** [`docs/superpowers/specs/2026-11-20-homey-app-design.md`](../specs/2026-11-20-homey-app-design.md)
(the design) and the Calvin design lead's UX and copy spec,
[`docs/design/2026-11-20-homey-app.md`](https://github.com/osterbergsimon/calvin/blob/design/homey-app/docs/design/2026-11-20-homey-app.md)
in the calvin repo (**the UI spec**, cited as *UI §n*; it moves to Calvin's `develop` when merged).
Executors read both, and Calvin's screen power mode design and spec on `develop`
(`docs/superpowers/specs/2026-11-21-screen-power-mode-design.md`,
`docs/design/2026-11-21-screen-power-mode.md`, `docs/integrations/HOME_AUTOMATION.md`).

**The UI spec predates the modes.** Its hold, "schedule paused" and back-to-schedule strings no
longer apply and are not built. The design marks every new or changed string **proposed**; a
proposed string is built as written but flagged in the PR for the design lead (design, "Open
questions" 3). Never write copy that is neither the UI spec's, Calvin's, nor a design-proposed
string.

## Global Constraints

- App id `xyz.wholab.calvin`; `"sdk": 3`; `"platforms": ["local"]`; `"compatibility": ">=12.9.0"`;
  `"permissions": []`; `brandColor` `#e08a1e` (UI §2).
- Driver id `screen`; capability ids `onoff`, `calvin_screen_power`, `alarm_calvin_offline`; flow
  card ids exactly as UI §5 for the cards that remain (`alarm_calvin_offline_true`,
  `alarm_calvin_offline_false`, `is_offline`, `all_on`, `all_off`) plus the design's
  `is_set_to_external`. These never change once released.
- The app never sends `{"power":"schedule"}` to a real screen and never changes a mode. The only
  `schedule` request is the connection check's probe to an id no screen has.
- A `409` from Calvin (`screen_power_always_on`, `screen_power_external`) is shown as Calvin's own
  `message`, never retried.
- Device `data` is `{ kioskId, connectionId }`; no address or key in `data`, store or settings.
- **Every user-facing string is copied verbatim from the UI spec**, section named in each task. If
  a string is missing there, stop and ask; do not write copy.
- The key appears only in `ManagerSettings` `connections` and in the `Authorization` header. Never
  in logs, errors, views, the settings page, tokens or capability values. The address is never
  logged.
- No user-facing text says "API" (except "API key"), "token", "endpoint", "hold", "held" or "paused"
  (the copy guard, Task 1.3).
- Poll every 30 000 ms; request timeout 5 000 ms; unreachable after 3 failed rounds; stop on the
  first key refusal.
- `redirect: "manual"`; certificate checks on; no runtime npm dependencies.
- Tests never contact a real Homey or Calvin: fake Calvin binds `127.0.0.1`, port 0. Test data uses
  `calvin.example`, `192.0.2.x` and ids like `kitchen-000000`. No household data.
- Pinned versions: `homey` CLI `4.6.3` (dev dependency), `actions/checkout`
  `3d3c42e5aac5ba805825da76410c181273ba90b1` (v7.0.1), `actions/setup-node`
  `949feb2413d6458794dcd2491c4babbbce0c15c1` (v7.1.0); every other dev dependency pinned exactly in
  `package.json` and locked in `package-lock.json`.
- Conventional Commits; no AI attribution; `scripts/check-commit-attribution.sh` passes.

## Review Focus

1. **Addresses as people type them**: `calvin.local:8000`, ` http://calvin.local:8000/ `,
   `HTTP://Calvin.Local:8000`, `192.0.2.10:8000`, `[2001:db8::1]:8000` all normalise; a path or
   credentials are refused. Test in Task 2.1.
2. **One bad round must not flip the tiles**: a single timeout or a Calvin restart leaves every
   device available; the third failed round in a row marks them unavailable. Test in Task 3.2.
3. **Fast toggles during a poll**: on, then off, while a poll that started earlier is still in
   flight; the device ends on the last command's answer. Test in Task 3.1.
4. **A revoked key with many screens**: the round stops at the first `401`, so Calvin sees one
   failed attempt per round, not one per screen; after a restart with `keyRefused` saved, no
   request is sent at all. Tests in Tasks 2.3 and 3.2.
5. **"All screens" when some cannot be reached**: no screens paired finishes without an error or
   a request; one unavailable screen among three gets no request and the card reports `1 of 3`;
   one failed `PUT` among three reports `1 of 3` too. A screen last seen in Always on is skipped
   silently: no request, and it is in neither count. Test in Task 5.2.
6. **A refused mode is shown, not retried**: a `PUT` that gets `409` throws Calvin's sentence once
   (one request, no retry), puts the tile back, and reads the screen at once so the mode row is
   current. Tests in Tasks 2.2 and 4.2.
